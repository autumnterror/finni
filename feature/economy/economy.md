# Economy

> Документ описывает существующий API и старую модель регулярных начислений. Контракт MVP 6.2, аудит расхождений и границы задач разработчика 1: [docs/features/economy.md](../../docs/features/economy.md). До реализации Week/Day вызов `processPeriodicIncome` из `GameSession` остаётся несовместимым с недельным циклом.

## Назначение

`feature:economy` — единственный источник финансового состояния FinPet. Модуль хранит доступный баланс, накопления, долг, расписание регулярного дохода, цели и неизменяемую историю операций. Другие фичи работают с деньгами только через `EconomyApi`.

## Границы ответственности

Economy отвечает за атомарное изменение денег, проверку достаточности средств, идемпотентность, регулярные начисления, погашение долга, переводы между собственными счетами, историю и сводку.

Economy намеренно не знает о магазине, предметах комнаты, питомце, заданиях, событиях и образовательных правилах. Вызывающая фича передаёт игровой смысл через `OperationContext.reasonId` и `metadata`; Economy проверяет только финансовые инварианты.

## Основные сущности

- `EconomyState`: доступные деньги, накопления, долг и `PeriodicIncome`.
- `FinancialOperation`: append-only запись изменения с before/after snapshots и дельтами всех финансовых частей.
- `SavingsGoal`: внешне идентифицируемая накопительная цель.
- `FinancialSummary`: текущее состояние, отфильтрованная история, доходы, расходы и изменение состояния.
- Денежные значения хранятся в рублях как `Long`. Дробных денежных единиц текущая продуктовая модель не использует.

## Публичный API

`EconomyFeature.getApi()` возвращает `EconomyApi`. API позволяет инициализировать, читать и наблюдать состояние; проверять и выполнять списания; пополнять баланс; создавать и погашать долг; переводить деньги в накопления и обратно; менять и обрабатывать регулярный доход; управлять целями; получать историю и сводку.

Каждая изменяющая деньги команда принимает непустой уникальный `operationId`. Повтор идентичной команды с тем же ID возвращает `AlreadyApplied` и не меняет данные. Повтор ID с другой суммой, типом или контекстом отклоняется как `OPERATION_ID_CONFLICT`. Для нового результата используются `Applied` и `Rejected` с явной причиной.

## Типы операций

- `opening_balance` — исходные деньги нового профиля, не доход;
- `credit` — внешнее разовое поступление;
- `debit` — внешний расход;
- `periodic_income` — валовое регулярное поступление;
- `debt_created` — получение денег в долг;
- `debt_repayment` — досрочное погашение из доступного баланса;
- `debt_auto_repayment` — удержание из регулярного поступления;
- `transfer_to_savings` и `transfer_from_savings` — внутреннее перемещение денег.

`FinancialOperationType` является value class со строковым кодом, поэтому историю можно расширять без изменения Room-схемы.

## Регулярные поступления

Расписание содержит положительную сумму, положительный период и timestamp следующего начисления. `processPeriodicIncome(now)` обрабатывает все сроки `<= now`. ID строятся из timestamp срока, поэтому восстановление приложения и повторный вызов не начисляют деньги ещё раз. Несколько пропущенных периодов выполняются в одной Room-транзакции. Параметры будущих поступлений меняются через `configurePeriodicIncome`.

## Долг

Одновременно допускается один активный долг, ограниченный `EconomyConfig.maximumDebtRub`. Создание долга одновременно увеличивает баланс и долг. Досрочное погашение может быть частичным; сумма сверх остатка долга отклоняется. Регулярное поступление сначала фиксируется полностью, затем отдельной операцией удерживается `min(поступление, долг)`. Результат отдельно сообщает валовой доход, погашение и реально полученную сумму.

## Накопления и цели

Перевод в накопления требует достаточного доступного баланса; возврат требует достаточных накоплений. Сумма `available + savings` при переводе не меняется, а переводы не входят в доходы и расходы сводки.

Цель имеет ID, название, положительную сумму, метаданные и признак активности. Прогресс строится по общей сумме накоплений: возвращаются сохранённая сумма, остаток, факт достижения и расписание дохода, достаточное для внешней оценки срока. Привязку цели к предмету выполняет другая фича через ID/metadata.

## История и сводка

Операция хранит ID, расширяемый тип, сумму, время, дельты баланса/накоплений/долга, полные снимки до и после, reason ID и metadata. `HistoryFilter` ограничивает полуоткрытый диапазон `[from, to)` и набор типов.

В сводке доходом считаются `credit` и `periodic_income`, расходом — `debit`. Долг и переводы не искажают доходы/расходы. `FinancialChange` отдельно показывает изменения доступных денег, накоплений, долга, всех денег и чистой стоимости.

## Инварианты и edge cases

- отрицательные и нулевые суммы отклоняются;
- пустой operation ID отклоняется;
- недостаток денег не создаёт частичного состояния или записи истории;
- состояние и история сохраняются одной Room-транзакцией;
- доступный баланс, накопления и долг не бывают отрицательными;
- долг не превышает конфигурационный лимит;
- арифметическое переполнение вызывает rollback;
- чтение пустого хранилища атомарно создаёт начальное состояние;
- миграция `6→7` переносит старый баланс и расписание из `game_sessions` и удаляет оттуда финансовые поля.

## Использование другими фичами

App-слой подключает `EconomyDependencies` через `EconomyMediator`. Feature должна получить `EconomyApi` через собственный dependency-контракт, придумать устойчивый operation ID и передать внешний контекст. DAO и entity не используются из presentation или чужой бизнес-логики.

## Тесты

Инструментальные тесты модуля проверяют начальное состояние и восстановление, пополнения и списания, недостаток средств, идемпотентность, некорректные суммы, несколько пропущенных периодов, повторную обработку, лимит и единственность долга, автоматическое частичное и досрочное погашение, накопления, цели, историю, фильтры, сводку и изменение расписания.
