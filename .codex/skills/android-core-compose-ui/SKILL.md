# Android Core Compose UI

Используй этот skill при создании или изменении визуального Compose UI. Он владеет правилами разметки, дизайн-системы и превью; не заменяет правила ViewModel, DI, навигации и хранения.

Не создавай и не обновляй README или документацию модуля/feature автоматически после реализации. Пиши их только по явному запросу пользователя; существующие документы можно читать как контекст.

## UI-тесты

- Не создавай и не изменяй Compose UI tests, Espresso tests и другие instrumented tests в `androidTest`, если пользователь отдельно и прямо не попросил написать UI-тесты.
- Не запускай `connectedAndroidTest`, `connectedDebugAndroidTest` и другие instrumented/UI-тесты без отдельного прямого запроса пользователя.
- Для обычной задачи по Compose UI ограничь автоматическую проверку компиляцией затронутых модулей, unit-тестами уже существующей логики и `checkDesignSystemUsage`. Визуальную проверку на доступном превью или эмуляторе можно выполнять вручную, не добавляя тестовый код.

## Перед правками

Проверь актуальные API, а не копируй оформление соседнего экрана вслепую:

| Файл или каталог | Зачем читать |
|------------------|--------------|
| `core/designsystem/README.md` | контракт дизайн-системы и существующие общие решения |
| `core/designsystem/src/main/java/github/detrig/designsystem/component/` | найди и прочитай компоненты, подходящие текущему UI |
| `core/designsystem/src/main/java/github/detrig/designsystem/theme/FinPetTheme.kt` | `FinPetTheme` и доступные свойства `AppTheme` |
| `core/designsystem/src/main/java/github/detrig/designsystem/theme/FinPetThemePack.kt` | заменяемый визуальный контракт |
| `build.gradle.kts` | существующая проверка `checkDesignSystemUsage` |

Если меняешь состояние, события или ViewModel — дополнительно читай `android-core-ui-mvvm`; если переходы между экранами — `android-core-nav3-routing`; если создание зависимостей — `android-core-feature-di`. Не загружай эти скиллы только ради правки оформления.

## Компоненты и дизайн-система

- `core:designsystem` — единственный источник повторно используемого оформления. В feature сначала используй существующие `FinPetButton`, `FinPetOutlinedButton`, `FinPetCard`, `FinPetIconButton`, `FinPetFeedbackSurface`, `FinPetProgressIndicator` и другие подходящие компоненты из `component/`.
- Не делай локальные копии кнопок, карточек, чипов, диалогов и индикаторов и не заменяй готовый FinPet-компонент сырым Material-компонентом. Material-реализация общих контролов остается внутри дизайн-системы.
- Если нужного варианта нет, сначала проверь параметры, slots и стили существующего компонента. При реальной общей потребности расширь его API или добавь небольшой переиспользуемый компонент в дизайн-систему; не переноси туда бизнес-логику feature.
- Используй `AppTheme.colors`, `typography`, `spacing`, `shapes`, `sizes`, `elevation` и `motion`. Цвета и стили выбирай по смыслу (`actionPrimary`, `textPrimary`, `screenTitle`), а не по названию палитры. Не обращайся напрямую к `MaterialTheme` из feature.
- Не хардкодь в feature брендовые цвета, шрифты, начертания, общие радиусы, тени и анимационные параметры. Не создавай локальную палитру или вторую тему ради одного экрана. Пока брендбук не утвержден, используй текущий theme pack, не изобретай новый бренд.
- Уникальные размеры конкретной композиции могут оставаться локальными. Повторяемые визуальные решения и требования доступности оформляй токенами; не добавляй отдельный токен для каждой координаты.
- Обычные Compose-примитивы разметки и рисования допустимы. Специфичное игровое изображение/Canvas остается в feature, но общие кнопки, текст и оформление используют дизайн-систему.
- Учитывай разные размеры экрана и увеличенный шрифт. Размеры touch-target бери из `AppTheme.sizes.minimumTouchTarget`/`preferredTouchTarget`; сохраняй семантику, подписи и disabled/loading-поведение компонентов.

## Граница визуального UI

Content/визуальные компоненты принимают готовые данные и callbacks. Получение ViewModel и подписка на состояние остаются в stateful Screen; UI не вызывает repository, DAO, сеть и глобальную навигацию напрямую. Не добавляй бизнес-логику или альтернативный state framework ради удобства верстки/превью.

## Compose Preview

- В каждом создаваемом или изменяемом Kotlin-файле, где Composable рисует экран, его Content или самостоятельный визуальный компонент, добавляй preview-функцию в этом же файле, а не только в отдельном `*Previews.kt`. Чистые route/router/DI/state-файлы без визуального UI превью не требуют.
- Предпочитай одну preview-функцию на экран/компонент для нескольких содержательных состояний: Content, Loading, Error, Empty и других реально существующих состояний. Передавай их через `@PreviewParameter` и компактный `PreviewParameterProvider` с детерминированными моками; переиспользуй имеющиеся фабрики preview-данных.
- Используй существующий `@PreviewAll` или аналогичную multipreview-аннотацию для конфигураций отображения. Такая аннотация сама не генерирует состояния: для разных UI-state нужен provider моков. Если `PreviewAll` отсутствует, подойдет доступный аналог или обычный `@Preview` с `@PreviewParameter`; не вводи новый фреймворк моков/кодогенерации ради превью.
- Не создавай отдельные методы `LoadingPreview`, `ErrorPreview`, `ContentPreview` и т. п., если состояния можно передать в одну функцию.
- Если provider/генератор моков и multipreview не удается разумно применить, допустима одна обычная `@Preview`-функция с заполненным Content-состоянием. Не оставляй файл вообще без превью или только с Loading.
- Оборачивай превью в `FinPetTheme`. Вызывай stateless Content с моками и пустыми обработчиками, без настоящей ViewModel, DI, БД, сети и побочных эффектов. Для stateful Screen превью рисует его Content; не поднимай весь runtime ради рендера.
- Не переделывай все старые экраны вне текущей задачи только ради нового правила.

## Проверка

- Убедись, что UI использует подходящие общие компоненты и семантические токены, а не их локальные дубликаты.
- Для изменений UI запусти доступную проверку `checkDesignSystemUsage` и компиляцию затронутого модуля, включая preview-код. Не исправляй несвязанные ошибки других модулей без отдельной задачи.
- При доступном рендере IDE проверь превью, в том числе важные состояния и увеличенный шрифт. Если рендер недоступен, не выдавай успешную компиляцию за визуальную проверку.
