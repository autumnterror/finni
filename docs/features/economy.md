# Feature: экономика и общие контракты MVP 6.2

## Цель

Единый кошелёк и журнал всех денежных изменений. Этот документ фиксирует контракты разработчика 1 из строк 6–7 плана Ганта и границы для следующих задач Week, Planning, Shop, Savings и Events. Ниже отдельно указано, что **уже реализовано**, а что является **целевым контрактом**.

## Образовательная цель

Ребёнок видит ограниченность денег и последствия выбора. Само начисление или списание не создаёт SkillId evidence; его записывает образовательный модуль по смыслу решения.

## Владение и модули

- `feature:economy` владеет остатками, атомарными денежными операциями, их историей и проверкой достаточности средств.
- Будущий владелец `Week` хранит игровую неделю, день, состояние недели и управляет rollover; Economy не выводит игровое время из часов телефона.
- Будущий владелец `WeeklyPlan` хранит черновик и подтверждённый план недели. План задаёт ориентиры, но не резервирует деньги в кошельке.
- Прикладной координатор отвечает за общую транзакцию, если покупка одновременно меняет Economy и Inventory/Pet/GameState; конкретное размещение координатора определяется интеграцией фич.
- Shop, Savings, Events и Side Jobs передают Economy стабильный ID и типизированное основание. Они не пишут в `economy_state` напрямую.
- `feature:game-state` уже проводит покупку зоны в общей Room-транзакции через `EconomyApi.debit`.
- `feature:product-market` пока показывает каталог/маршрут магазина и баланс; подтверждённая оплата и холодильник отмечены в его README как последующая работа.

## Уже реализовано на 18.09.2026

- `EconomyApi`: чтение/Flow, `credit`, `debit`, переводы, долг, история, сводка и цели.
- Room-таблицы `economy_state`, `financial_operations`, `savings_goals`; операции и остаток сохраняются одной транзакцией.
- Первичный ключ операции защищает от повторного списания, отрицательный остаток и неположительная сумма отклоняются.
- У операций есть дельты и снимки `before/after`; у экономики есть инструментальные тесты.
- Новое начальное состояние теперь создаёт запись `opening_balance`; сравнение повтора учитывает тип, сумму и контекст; сводка читает состояние и журнал из одной транзакции.

## Целевые общие модели

Это контракт для согласования с командой, **не существующий Kotlin API**. Имена и размещение согласуются до использования в соседних фичах.

```kotlin
@JvmInline value class Money(val rub: Long) // rub >= 0; только целые игровые рубли

data class WeekId(val value: String) // стабильный ID, не timestamp
enum class GameDay { MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY, SATURDAY, SUNDAY }
enum class WeekStatus { PLANNING, ACTIVE, COMPLETED, EARLY_FINISHED }

data class Week(
    val id: WeekId,
    val number: Int,
    val day: GameDay,
    val status: WeekStatus,
    val startingWallet: Money, // остаток до выплаты новой недели
    val allowanceGross: Money,
    val allowanceDebtRepayment: Money,
    val plan: WeeklyPlan?,
)

data class WeeklyPlan(
    val weekId: WeekId,
    val availableAtPlanning: Money, // кошелёк после выплаты и удержания долга
    val mandatory: Money,
    val optional: Money,
    val savings: Money,
    val confirmed: Boolean,
) {
    val freeRemainder: Money // availableAtPlanning - mandatory - optional - savings
}
```

Правила: сумма плана не превышает `availableAtPlanning`, все суммы неотрицательны, арифметика проверяется на переполнение. Подтверждение возможно один раз для `WeekId`; после него план неизменен. Перевод в копилку выполняется отдельной денежной операцией и не происходит автоматически при подтверждении плана. Новая неделя начинается после результата предыдущей; одно завершение дня не выдаёт доход.

## Контракт транзакции

Целевая запись должна иметь: `operationId`, `profileId`, `weekId`, `gameDay`, тип, сумму, источник/причину, категорию расхода, дельты кошелька/накоплений/долга, `before/after`, порядок внутри игрового дня. В существующей БД есть ID, тип, сумма, timestamp, дельты, снимки и два свободных строковых поля; остальные поля требуют миграции.

Рекомендуемые типы: `OPENING_BALANCE`, `WEEKLY_ALLOWANCE`, `PURCHASE`, `SIDE_JOB_REWARD`, `EVENT_INCOME`, `EVENT_EXPENSE`, `SAVINGS_DEPOSIT`, `SAVINGS_WITHDRAWAL`, `DEBT_CREATED`, `DEBT_REPAYMENT`. Для расхода обязательна категория `MANDATORY` или `OPTIONAL`; для покупки нужен `itemId`. Доход, внутренний перевод и долг не считаются расходом магазина. `Plan ↔ Actual` собирается из сохранённых операций этой недели, а не из текущего остатка или времени телефона.

`operationId` задаёт инициатор по бизнес-событию, например `week:<weekId>:allowance`, `purchase:<purchaseId>`, `event:<eventId>:<choiceId>`, `side-job:<completionId>`. Повтор того же ID и того же неизменяемого payload возвращает `AlreadyApplied`; повтор с другим payload возвращает `OPERATION_ID_CONFLICT`. UI создаёт ID до подтверждения и сохраняет его до результата, а не генерирует новый при каждом тапе. `canDebit` служит подсказкой для UI; результат `debit` остаётся окончательным из-за возможной гонки.

Денежная команда возвращает `Applied(operation, state)`, `AlreadyApplied(operation, state)` или `Rejected(reason, state)`; отклонение не создаёт запись и не меняет остаток. При нехватке денег вызывающая фича показывает недостающую сумму и допустимые действия. Экономика не запрещает доступную необязательную покупку только из-за отклонения от плана.

## Контракт междоменных действий

| Сценарий | Инициатор | Что передаёт в Economy | Что делает после успешного списания/начисления |
|---|---|---|---|
| Покупка | Shop/координатор | ID покупки, цена, `weekId`, `itemId`, категория | Сохраняет предмет/запас еды в той же общей транзакции |
| Копилка | Savings | ID перевода, `weekId`, сумма | Обновляет цель только если это отдельный выбор игрока; перевод не доход |
| Подработка | Notebook/координатор | ID завершения, `weekId`, награда | Лимит оплачиваемых заданий проверяет владелец Side Jobs |
| Событие | Events/координатор | ID разрешённого выбора, `weekId`, эффект | Сохраняет исход, feedback и evidence атомарно или через идемпотентный outbox |
| Новая неделя | Week/координатор | `week:<id>:allowance`, валовая сумма, удержание долга | Фиксирует статус PLANNING; план создаётся после выплаты |
| Кровать | Week | Денежной команды нет | Меняет день, потребности и события; при воскресенье завершает неделю |

## UI

Экономика не владеет экраном. HUD показывает доступный баланс, телефон — краткую историю. Перед покупкой Shop показывает цену, категорию, эффект и баланс после покупки; подтверждение обязательно. Ошибку нехватки средств преобразует экран, вызвавший операцию.

## Persistence и миграции

Текущее состояние и журнал в Room, схема общей БД v10. `9→10` переносила старый баланс, но не создавала достоверную запись о происхождении перенесённой суммы. Новые установки получают `opening_balance`; для старых профилей история до миграции может не объяснять текущий остаток полностью. Перед введением полей `weekId/category` нужна миграция без сброса прогресса. Для legacy-операций категория будет `UNKNOWN`, `weekId` — отсутствующим; нельзя приписывать их текущей неделе задним числом.

## События, SkillId и конфигурация

Операция может быть источником `behaviourEvidence`, но Economy не меняет mastery или XP. `EconomyConfig` сейчас задаёт стартовые 500 ₽ и периодический доход по миллисекундам; целевая конфигурация задаёт выплату за **игровую неделю** и балансировку отдельно. Цены и награды не должны находиться в Compose-коде.

## Критические расхождения с MVP 6.2

1. `GameSession` вызывает `processPeriodicIncome(System.currentTimeMillis())` при открытии. Даже если вызов идемпотентен по timestamp, он выдаёт деньги по реальным часам. В задаче Week/Day его нужно удалить и заменить единственным rollover по `WeekId`.
2. `PeriodicIncome`, `nextAtMillis` и обратный отсчёт в HUD/диалоге покупки описывают старую механику. Они пока оставлены для совместимости; UI должен перейти на игровой день/неделю.
3. `credit/debit` пока не имеют обязательных `weekId`, категории и предмета. Поэтому недельный `Plan ↔ Actual` из текущей истории надёжно посчитать нельзя.
4. `createDebt` доступен любому вызывающему коду без проверки важной покупки; правило допуска должно появиться в контекстном Debt use case, не в кнопке общего кредита.
5. Стартовые 500 ₽ сейчас создаются при инициализации Economy, а недельная выплата тоже настроена на 500 ₽. При переходе на первую игровую неделю нужно выбрать один путь выдачи начальных денег, чтобы не удвоить бюджет.
6. `summary` включает начальный остаток в дельты и не считает его доходом. Недельный итог должен использовать фильтр по `weekId` и отдельное поле `startingWallet`.

## Edge cases и критерии приёмки пункта 2

- Двойной тап/рестарт с тем же ID и payload создаёт одну запись и одно изменение денег; другой payload с тем же ID отклоняется.
- Одновременные списания не уводят кошелёк ниже нуля; отказ не добавляет предмет.
- Каждое новое изменение денег имеет запись с согласованными `before/after` и дельтами. Внутренний перевод сохраняет общую сумму.
- Начальная сумма новой установки отражена отдельной записью и не считается заработком.
- После закрытия и открытия приложения состояние и операции сохраняются; операция с тем же ID не повторяется.
- Проверка через `canDebit` не заменяет результат фактического списания.
- Для перехода на недельную механику требуются отдельные проверки: семь дней без выплаты, один allowance на новую неделю, удержание долга не дважды, восстановление в середине rollover.
