# Feature: обучение через достижения

## Статус

Общая инфраструктура Learning реализована 19.09.2026: отдельный модуль и ручной
DI, каталог из 24 достижений, конфигурируемый вычислитель порогов, Room-хранилище,
идемпотентная обработка действий, готовые строки для родительского кабинета,
first-time explanations и надёжный XP outbox.

Правила недельного плана и формирования сбережений подключены в production.
Копилка сообщает о подтверждённой цели, пополнении и достижении суммы; планирование
сообщает о положительной сумме сбережений в плане. Источники повторно передают
сохранённые факты после перезапуска, а Learning убирает дубликаты. Альбом и
временное уведомление о достижении доступны в игре. Родительский кабинет и
`ProgressionApi` ещё не реализованы; XP остаётся в outbox.

## Цель

Превращать реальные финансовые действия ребёнка в устойчивый образовательный
прогресс:

```text
действие → игровое последствие → объяснение питомца → достижение → строка родителю
```

Обучение не должно становиться отдельной викториной и не должно дублировать
бизнес-правила планирования, экономики, накоплений или магазина.

## Образовательная цель

На текущем этапе поддерживаются четыре темы:

- планирование бюджета;
- формирование сбережений;
- платежи и покупки;
- финансовая безопасность.

У каждой темы есть измеримые действия. У обычного действия два шага и два
достижения: «ознакомился» и «научился». Для финансовой безопасности прогресс
состоит из трёх шагов — объяснение, самостоятельная реакция, закрепление — но
достижений всё равно два.

Каждое впервые открытое достижение выдаёт настраиваемое количество XP. XP остаётся
игровой прогрессией, а достижение — образовательной записью. Повторное получение
того же достижения не выдаёт XP ещё раз.

## Что требуется от обвязки сейчас

### 1. Отдельный модуль и ручной DI

Реализован `:feature:learning` в существующем стиле проекта:

- `LearningFeature`;
- `LearningDependencies`;
- `LearningComponent`;
- `LearningModule`;
- `LearningApi` и `LearningApiImpl`;
- repository, DAO, entities и чистый rule evaluator.

Зависимости предоставляет `app` через `LearningMediator` и
`ModuleDependenciesProvider`. Learning не зависит от UI-модулей
Planning, Savings, Shop или Events. Прикладные координаторы передают ему только
факты уже завершившегося действия.

На этом этапе не нужна общая шина событий. Интеграция использует прямой
`LearningApi`, но значимое действие нельзя доставлять по принципу fire-and-forget.
Координатор должен либо зафиксировать бизнес-результат и learning action в одной
транзакции общей Room-базы, либо записать source outbox вместе с бизнес-результатом
и повторять доставку после восстановления. Идемпотентность `LearningApi` делает
такой повтор безопасным.

### 2. Версионируемый каталог достижений

Каталог — единственное место, где задаются:

- стабильный `achievementId`;
- тема и метрика;
- этап `INTRODUCTION` или `LEARNED`;
- правило/порог;
- ключ награды XP;
- текст для ребёнка;
- отдельный завершённый текст для родительского кабинета.

Тексты и пороги нельзя дублировать в исходных фичах. При старте приложения каталог
должен валидироваться: ID уникальны, у каждой активной метрики есть ровно два
достижения, у каждого достижения есть непустая родительская строка и XP-награда.

В БД сохраняются ID и факты открытия, а не копия текста. Это позволяет менять
формулировки и локализацию без миграции пользовательского прогресса. Удалять или
переиспользовать опубликованный ID нельзя.

### 3. Расширяемый входной контракт

Источник сообщает не «добавь балл», а неизменяемый факт с контекстом, достаточным
для централизованного правила:

```kotlin
@JvmInline
value class LearningActionType(val value: String)

interface LearningActionContext {
    val fingerprint: String
}

data class LearningAction(
    val actionId: String,
    val profileId: String,
    val gamePeriod: Long,
    val type: LearningActionType,
    val context: LearningActionContext,
    val sourceOperationId: String? = null,
)
```

Для каждой темы добавляются стабильные типы действий и типизированные реализации
`LearningActionContext`. Например, Savings должен объявить контексты создания
цели, планирования накоплений, успешного пополнения и достижения цели. Общая часть
хранит fingerprint для проверки идемпотентности, а содержательное решение о том,
засчитывать ли действие, остаётся в правиле Learning, а не в UI Savings.

`actionId` создаётся из устойчивого ID бизнес-операции или сценария, а не из
текущего времени. Повтор с тем же ID и тем же payload возвращает прежний результат.
Тот же ID с другим payload считается конфликтом и ничего не меняет.

Минимальный API:

```kotlin
interface LearningApi {
    suspend fun record(action: LearningAction): RecordLearningResult
    fun observeAchievements(profileId: String): Flow<List<AchievementProgress>>
    fun observeParentRows(profileId: String): Flow<List<ParentProgressRow>>
    fun observePendingXpRewards(profileId: String): Flow<List<PendingXpReward>>
    suspend fun claimFirstExplanation(profileId: String, explanationId: String): Boolean
    suspend fun deliverPendingXpRewards(profileId: String): XpDeliveryResult
    suspend fun resetProfile(profileId: String)
}
```

`record` возвращает новое состояние метрик, впервые открытые достижения, ключи
короткой обратной связи и новые XP-награды. UI не вычисляет эти результаты.

### 4. Чистый вычислитель правил

Реализованный rule evaluator получает конфигурацию метрик и журнал подходящих
игровых периодов, затем детерминированно вычисляет число действий, разные периоды,
текущий streak и достигнутый progress step. Он не обращается к Compose, навигации,
часам устройства или другим feature API.

Общие правила:

- одно бизнес-действие квалифицируется не более одного раза;
- первый управляемый опыт может открыть «ознакомился»;
- «научился» требует повторения, самостоятельного выбора или применения в другом
  условии;
- количество повторений и игровых периодов задаётся конфигурацией;
- ошибки дают объяснение и возможность повторить, но не уменьшают прогресс;
- открытие экрана, показ подсказки и чтение текста не являются действием;
- решение о покупке оценивается по контексту, а не по простому `купил/отказался`.

Для плана отдельно оцениваются качество исходного плана и следование ему. Нельзя
выдавать «научился следовать плану» только за совпадение плохого плана с плохими
расходами.

### 5. Persistence и атомарность

Общая Room-база версии 14 содержит таблицы:

| Таблица | Назначение |
|---|---|
| `learning_actions` | Inbox обработанных действий; `actionId` — primary key, хранится digest payload для обнаружения конфликта |
| `learning_metric_occurrences` | Журнал квалифицирующих действий по метрике и игровому периоду для пересчёта repeats/distinct periods/streak |
| `learning_metric_progress` | Текущие шаги, число подходящих повторов, разные игровые периоды, streak и последний период |
| `achievement_unlocks` | Открытие достижения, исходное действие и игровое время; уникальность по профилю и achievement ID |
| `learning_explanations` | Какие первые объяснения уже были показаны |
| `achievement_xp_outbox` | Идемпотентная доставка XP после открытия достижения |

Обработка действия, изменение метрик, открытие достижения и создание записи XP
outbox выполняются в одной транзакции. Доставка XP может быть повторена после
перезапуска. Её стабильный ID имеет вид, эквивалентный
`achievement-xp:<profileId>:<achievementId>`.

До вызова `record` источник также гарантирует доставку одним из двух способов:

- общая транзакция доменного координатора;
- маленький source outbox, записанный атомарно с исходной операцией.

Простой вызов после commit без возможности восстановления недостаточен: процесс
может завершиться между финансовой операцией и записью образовательного прогресса.

Миграция `13 → 14` реализована без сброса данных и покрыта instrumentation test.

### 6. Мост в игровую прогрессию

Сейчас в проекте есть `playerLevel`, но нет полноценного хранилища XP и публичного
идемпотентного метода начисления. В Learning уже есть `LearningXpRewardGateway` с
результатами `Granted`, `AlreadyGranted` и `RetryLater`. App-mediator временно
возвращает `RetryLater`, поэтому награда сохраняется и не считается доставленной.
Будущий владелец прогрессии должен предоставить контракт, эквивалентный:

```kotlin
interface ProgressionApi {
    suspend fun grantXp(grantId: String, amount: Int): GrantXpResult
    fun observeProgress(): Flow<GameProgress>
}
```

Его можно разместить в существующем `feature:game-state` или выделить позже в
отдельный модуль прогрессии. Learning только запрашивает награду; пороги уровня и
стадии питомца остаются у владельца игровой прогрессии.

### 7. Обратная связь питомца

Общий компонент диалога уже можно переиспользовать. Learning возвращает ключ
сообщения и флаг первого объяснения, а экран-координатор решает, когда показать
диалог. Сам Learning не зависит от Pet UI.

Первое появление механики получает объяснение. В сценариях мошенничества питомец
сначала сообщает, что ситуация выглядит подозрительно, затем объясняет риск. Для
накоплений допустимо дружелюбное напоминание, но нельзя вызывать чувство вины или
связывать любовь питомца с покупкой желаемого предмета.

### 8. Родительский кабинет

Нужен отдельный consumer `LearningApi`, будущий `:feature:parent`. Он группирует
строки по темам, но не пересчитывает правила и не читает таблицы напрямую.

Каждое открытое достижение создаёт отдельную строку. Агрегат вроде «тема 3/6» может
быть дополнительным, но не заменяет формулировки «Ребёнок ознакомился…» и
«Ребёнок научился…». Закрытые достижения нельзя показывать как уже освоенные;
при необходимости для них используется нейтральный статус «в процессе».

## Интеграция с существующими фичами

| Источник | Что уже есть | Что нужно добавить |
|---|---|---|
| Planning | сохранение плана и фактические суммы | action после подтверждения; оценка достаточности обязательных расходов; итоговая оценка качества плана и следования ему |
| Week / Week Summary | детерминированная неделя и день | итог периода с причинами отклонений, а не только абсолютной разницей |
| Savings | цель, переводы, прогресс | actions создания цели, успешного пополнения и первого достижения суммы; связь с плановой суммой накоплений |
| Product Market / Shop | подтверждённая покупка и operation ID | снимок обязательных нужд, корзины, бюджета, дней до конца недели и влияния решения |
| Events | пока нет общего модуля | типизированные акции, импульсивные желания, изменения бюджета и два сценария безопасности |
| Dialogue / Pet | общий диалог и портрет питомца | показ feedback по ключу и атомарный `claimFirstExplanation` |
| Game State / Progression | уровень игрока без XP API | идемпотентное начисление XP и вычисление уровня/стадии |
| Parent | модуля пока нет | экран, который наблюдает готовые `ParentProgressRow` |

### Обнаруженные разрывы текущей модели

1. Текущий Planning требует, чтобы три процента всегда давали 100 %. Поэтому
   финансовая подушка не представлена отдельно. Для правил обучения нужно либо
   разрешить сумму меньше 100 % и считать остаток резервом, либо добавить явную
   четвёртую категорию. Предпочтителен свободный остаток: он уже согласуется с
   общим контрактом недельного плана и не требует четвёртого вида расходов.
2. Текущий статус плана основан в основном на величине превышения. Для обучения
   нужна причина отклонения: обязательное событие, осознанный выбор или импульс.
3. `adapt_to_change`, акции, импульсивные желания и финансовая безопасность требуют
   контента событий; Learning сам не должен генерировать эти события.
4. Для разумной покупки недостаточно одной денежной транзакции. Нужен снимок
   потребностей и обязательств в момент решения.
5. Для XP нужна отдельная идемпотентная точка записи; прямое изменение
   `playerLevel` из Learning запрещено.

## Конфигурация

В конфигурацию выносятся:

- XP за каждое достижение;
- число повторений и разных игровых периодов для второго достижения;
- допустимое отклонение от плана;
- критерии адекватного плана и достаточной подушки;
- набор событий, засчитываемых как изменённые условия;
- порядок демонстрационных событий;
- активность отложенных метрик.

## Edge cases

- Одно действие может обоснованно продвинуть несколько метрик, но каждую не более
  одного раза.
- Повтор callback, двойной тап или восстановление процесса не дублирует прогресс.
- Один action ID с другим payload отклоняется как конфликт.
- Неудачная денежная операция не создаёт LearningAction.
- Подсказка может показать объяснение, но сама по себе не открывает достижение,
  кроме явно описанного управляемого первого опыта.
- Отказ от необязательной покупки не считается автоматически правильным;
  доступная разумная покупка тоже может быть корректным решением.
- Первая безопасная ситуация управляемая, вторая самостоятельная, третья должна
  быть отдельным поздним сценарием.
- Изменение текста родителю не требует переписывать факты открытия.
- Неизвестный ID из более новой версии БД сохраняется и не сбрасывает профиль.
- Demo reset удаляет learning-прогресс и связанные XP-гранты тестового профиля,
  но не должен затрагивать обычный профиль.

## Тесты

### Уже покрыто

- каталог содержит 24 уникальных достижения и полный parent mapping;
- обычная метрика открывает этапы на шагах 1 и 2, безопасность — на шагах 1 и 3;
- разные игровые периоды и streak считаются по `gamePeriod`, а не по часам устройства;
- повтор действия, конфликт payload и повтор XP delivery обрабатываются
  идемпотентно;
- action, progress, unlock и XP outbox фиксируются одной Room-транзакцией;
- родительский Flow выдаёт отдельную строку для каждого открытия;
- первое объяснение выдаётся один раз, reset очищает learning-состояние профиля;
- неподдерживаемый action не занимает свой ID и может быть повторён после
  добавления правила;
- миграция `13 → 14` открывается Room и сохраняет существующую схему.

Проверены JVM-тесты каталога и rule engine, Android-тест repository на in-memory
Room и migration test приложения.

### Добавить вместе с конкретными темами

- committed game action не теряет learning action при остановке процесса между
  исходной операцией и обработкой Learning;
- неудачная денежная операция не создаёт learning action;
- создание цели, планирование, регулярное пополнение и достижение цели используют
  разные типы действий и метрики;
- закрытие цели и регулярные пополнения считаются раздельно;
- плохой план не открывает `reasonable_plan.learned`;
- точное следование плохому плану не считается полным успехом;
- обоснованное отклонение не приравнивается к импульсивному;
- восстановление реального `ProgressionApi` доставляет недоданную XP один раз;
- полный demo reset согласованно очищает Learning и XP тестового профиля.

## Что пока не нужно

- удалённый backend и синхронизация;
- ML/адаптивный подбор сценариев;
- универсальная event-bus инфраструктура;
- редактор достижений для контент-менеджера;
- числовая оценка ответственности, мотивации или характера ребёнка;
- отдельная аналитическая модель поверх достижений;
- проверка чеков до появления механики чека.

## Решения, которые нужно фиксировать при подключении правил

1. Сколько повторов и игровых периодов означает «научился» для каждой метрики.
2. Должны ли периоды идти подряд или достаточно нескольких разных периодов.
3. Что именно считается адекватным планом и какой размер подушки достаточен.
4. Как засчитывается второе достижение `reach_goal`: вторая цель, более сложная
   цель или самостоятельное прохождение первой цели без подсказок.
5. Сколько XP даёт каждое достижение и как XP преобразуется в уровень питомца.
6. Показывается ли ребёнку отдельный альбом/попап достижений или только короткое
   празднование в текущем экране.

Техническая обвязка от этих решений не зависит: XP, пороги и milestone rules уже
конфигурируются. Значение XP по умолчанию `10` является временной настройкой, а не
зафиксированным балансом продукта.

## Критерии приёмки обвязки

- Все 24 текущих достижения имеют стабильный ID, этап, порог каталога, XP-награду
  и строку родителю; содержательные правила активируются по мере интеграции тем.
- После подключения исходные фичи сообщают факты, но не меняют счётчики Learning
  напрямую.
- Повтор одного действия не меняет прогресс и не выдаёт XP повторно.
- Будущий родительский кабинет получает готовые строки через API и не знает о
  порогах.
- Первое объяснение механики показывается один раз и переживает перезапуск.
- Прогресс, открытия и ожидающие XP-награды восстанавливаются из Room.
- Общая логика порогов покрыта чистыми JVM-тестами, repository и миграция —
  instrumentation tests; содержательные правила темы получают отдельные тесты при
  подключении.
